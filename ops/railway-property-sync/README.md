# 物件同期：Railway Cron代替案（**未デプロイ**）

このディレクトリは、GitHub Actionsの30分間隔スケジュールが繰り返し欠落する際に使う **専用Railway Cronサービスの候補**です。既存のメール監視・スクレイピング用Railwayサービスとは独立します。

- `run.sh` は新しい `POST /api/internal/property-sync-and-wait` を使用します。
- HTTP 200かつ `complete: true`、`failed: 0`、更新件数が1件以上の場合だけ正常終了します。
- `CRON_SECRET` は専用RailwayサービスのSecret Variablesに管理し、ログやリポジトリに値を出しません。
- `railway.json` はUTCの毎時17分と47分に実行する設定です。時間帯は日本でも17分・47分です。
- 終了する一回限りのCronプロセスであり、常駐ワーカーではありません。同期APIの待機上限は330秒で、Vercel専用関数の300秒上限より余裕を設けています。

## 本番導入前の確認

1. PR #20の完成判定APIを隔離テストし、プレビュービルド成功を確認する。同期専用のVercel関数だけ最大300秒（既存公開APIは60秒）とし、実運用では完了時間と失敗件数を計測する。300秒を超える場合はジョブ分割を検討する。
2. PR #20を本番反映した後、GitHub Actionsから新APIを使った少なくとも1回の同期について、実際のDB反映と成功レスポンスを確認する（例外的な手動同期を行う場合は別途判断する）。
3. GitHub Actionsの定期実行が復旧せずRailwayへ移す場合、**先にGitHub側の自動同期を無効化**して二重起動を防ぐ。
4. このディレクトリを**新規**Railwayサービスのルートとし、既存のmail/scrapeサービスのコード・設定・変数には触れない。
5. 新規サービスに `CRON_SECRET` を安全に設定し、Cronを `17,47 * * * *`（UTC）で有効化する。
6. Railwayの直近2回以上の完了ログと、Supabaseの物件反映状況を照合する。同期失敗時にはRailwayのジョブ終了コードを調べる。
7. Railwayを稼働させた後は、GitHub Actionsで同期実行を再度有効化しない。
